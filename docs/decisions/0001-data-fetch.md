# 0001. Выгрузка сырых данных из OpenDota

Дата: 2026-10-10. Статус: принято.

## Контекст

Помощнику нужны данные по нашим игрокам и соперникам (5 + 5 человек) и общая картина текущего патча.
Что именно понадобится для анализа, заранее неизвестно, поэтому сначала сохраняем всё, что отдаёт API,
без преобразований. Бесплатный лимит OpenDota: 60 запросов в минуту, 3000 в день (так говорят заголовки
`X-Rate-Limit-Remaining-Minute` / `-Day`).

## Решения

**Стек.** Java 21 и Gradle (Kotlin DSL, wrapper 8.10.2). HTTP — встроенный `java.net.http.HttpClient`,
внешняя зависимость не нужна. JSON и YAML — Jackson (`jackson-databind` + `jackson-dataformat-yaml`):
одна библиотека на оба формата. Ответы пишем байт в байт, Jackson только проверяет, что это валидный JSON,
а не `{"error": …}`.

**Сохраняем как есть.** Один запрос → один файл, атомарная запись через `.tmp`. Обрыв не оставляет
полуфайла, который при следующем запуске сочли бы скачанным. Без `--refresh` существующие файлы пропускаются.

**Лимиты.** Пауза 1,1 с между запросами. На 429 и 5xx — до 5 повторов с паузой 2, 4, 8, 16, 32 с (или
`Retry-After`, если он больше). Остаток лимита из заголовков пишется в лог на каждый запрос. Если
минутный остаток равен 0, ждём 60 с.

**`/players/{id}/matches`.**
- `significant=0`. По умолчанию (1) API отбрасывает нестандартные режимы и матчи. Нам нужны все матчи,
  фильтровать будем сами по `game_mode` / `lobby_type`.
- `project`. В документации — только «Fields to project (array)», без списка. Список подобран перебором
  около 180 кандидатов (поля матча и игрока из OpenAPI-спеки + колонки `player_matches` из `/schema`).
  Неизвестные поля API молча отбрасывает. Принято 53 поля, плюс всегда приходят `match_id`,
  `player_slot`, `radiant_win`. Список — в `Endpoints.MATCH_FIELDS`.
- Пагинация не нужна: все ~9500 матчей приходят одним ответом (~16 МБ, около 10 с).

**Агрегаты** (`heroes`, `peers`, `counts`, `totals`) — с параметрами по умолчанию (`significant=1`).
Агрегат потом не перефильтровать, а «стандартные» матчи (All Pick, Ranked, Captains Mode…) — именно то,
что отражает силу игрока. Сырые матчи со `significant=0` покрывают остальное. `wl` качаем со
`significant=0`, чтобы сверять его с числом записей в `matches.json`.

**Дополнительные эндпоинты игрока:** `wl` (сверка), `counts` (готовые разбивки по линии/режиму/патчу),
`totals`, `ratings` (история ранга), `rankings` (перцентиль на героях). Не берём: `recentMatches`
(подмножество matches), `pros`, `wordcloud` (чат), `histograms` (выводятся из matches), `wardmap`
(тяжёлый, понадобится разве что для саппортов).

**Мета патча** — `data/meta/{patch}/`, текущий патч = последний элемент `constants/patch.json`.
- `/heroStats` и `/scenarios/laneRoles` — как есть. Это агрегаты OpenDota за последние дни, мы их не
  фильтруем.
- Синергии и контрпики в API готовыми не отдаются (`/heroes/{id}/matchups` считается только по
  про-матчам, и это 127 запросов). Поэтому считаем их SQL-запросами через `/explorer` по таблице
  `public_matches` (`radiant_team`/`dire_team` — массивы героев): последние N match_id, средний ранг
  ≥ Legend, `start_time` ≥ начала патча. Три запроса: базовый винрейт героя, пары в одной команде,
  герой против героя (порог 30 игр на пару). Выборка `count(*)` по всему патчу упирается в таймаут
  explorer (~15 с), поэтому окно по match_id: 1 млн id ≈ 250 тыс. матчей, ≈ 6–8 с на запрос.
- Параметры выборки пишем в `_sample.json`: без них цифры из synergy/counters нельзя честно читать.

## Последствия

- Весь прогон по 10 игрокам — около 100 запросов из 3000 дневных.
- Агрегаты и мета отражают момент скачивания. Для свежих данных нужен `--refresh`.
- Перед турниром всё стоит перекачать с `--refresh`. Если вышел новый патч, мета ляжет в новую папку,
  старая останется для сравнения.
- Если OpenDota начнёт принимать новые поля в `project`, список придётся обновить вручную.
