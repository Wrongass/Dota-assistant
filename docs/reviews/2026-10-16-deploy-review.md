## Приоритет P0 — обновление данных

Сейчас deploy/update-data.sh выполняет:

    docker compose run --rm fetch

Но fetch без --refresh пропускает уже существующие файлы. В результате ежедневный cron после первой загрузки фактически не обновляет данные.

Исправить:

1. Плановое обновление должно запускать fetch с --refresh.
2. После успешного обновления web должен перечитать данные или перезапуститься.
3. При неуспешном fetch web не должен перезапускаться.
4. Добавить тест или автоматическую проверку, которая не позволит снова потерять --refresh.
5. Исправить соответствующие команды и комментарии в README, Compose, docs/deploy.md, ADR и скриптах.

Сделать обновление набора данных транзакционным:

- сейчас отдельные JSON-файлы записываются атомарно, но весь набор данных — нет;
- при ошибке в середине --refresh на диске остаётся смесь старых и новых файлов;
- загружать новую генерацию во временный каталог;
- проверить её целостность;
- публиковать её целиком только после полного успешного fetch;
- при ошибке активная генерация должна остаться неизменной;
- исключить одновременный запуск двух fetch-процессов;
- предусмотреть понятный rollback/cleanup временной генерации.

## Приоритет P1 — воспроизводимость и CI

1. Исправить executable bit у gradlew:
   git update-index --chmod=+x gradlew.
2. Добавить GitHub Actions:
   - JDK 21;

   - сборка приложения;
   - сборка Docker image;

4. Добавить минимальные тестовые fixtures для основных web/auth smoke-тестов, чтобы критические маршруты не пропускались полностью из-за отсутствия production-data.
5. Зафиксировать или верифицировать Gradle dependencies: dependency locking и/или dependency verification.
6. Закрепить Docker base images по digest либо документировать контролируемый механизм их обновления.
7. Не публиковать image и не выполнять deployment из PR без отдельного явного разрешения.

## Приоритет P1 — Docker hardening

Обновить production Docker/Compose-конфигурацию:

- runtime-контейнер должен работать не от root, например UID/GID 10001;
- root filesystem — read-only;
- cap_drop: ALL;
- no-new-privileges;
- отдельный writable mount только для fetch/data;
- web должен получать data read-only;
- добавить разумные memory, CPU и PID limits;
- /tmp предоставить через ограниченный tmpfs, если он необходим;
- порт приложения публиковать только на 127.0.0.1, никогда не на 0.0.0.0 хоста;
- добавить healthcheck или документированный эквивалент для /health;
- проверить корректное завершение приложения по SIGTERM.

Fetch и web могут использовать один image, но должны иметь разные права доступа к data.

## Приоритет P1 — authentication hardening

Проверить и улучшить реализацию dota.web.Auth:

1. Не использовать простой SHA-256 как password verifier. Применить подходящий password KDF, например Argon2id, scrypt или PBKDF2 с корректными параметрами и солью.
2. Отделить ключ подписи сессий от пользовательского пароля. Добавить отдельный SESSION_SECRET либо безопасно генерируемый и сохраняемый session key.
3. Сохранить возможность инвалидировать все сессии при смене credentials.
4. Убрать Thread.sleep(500) из HTTP request handler: блокировка worker thread не должна использоваться как защита от перебора.
5. Сделать rate limiter ограниченным по памяти и автоматически удалять устаревшие IP-записи. Сейчас карта failures может расти без ограничения.
6. Явно определить доверие к X-Forwarded-For и X-Forwarded-Proto. Не доверять forwarded headers от произвольного клиента; учитывать их только за настроенным trusted proxy.
7. Добавить тесты:
   - HttpOnly;
   - SameSite;
   - Secure за HTTPS reverse proxy;
   - истечение сессии;
   - смена credentials;
   - rate limit и очистка его состояния;
   - защита от spoofed forwarded headers;
   - отсутствие open redirect.
8. Logout желательно сделать POST или обосновать безопасный GET-вариант.
9. Добавить подходящие security headers в официальный proxy-конфиг, включая CSP после проверки совместимости интерфейса.

## Приоритет P1 — документация

Исправить обнаруженные неточности:

- в docs/deploy.md указан неправильный URL:
  `https://github.com/Wrongass/test2.git`;
- заменить его на актуальный репозиторий;
- описание «≈140 запросов, пара минут» не соответствует текущей конфигурации с 20 игроками, лигой и метой: первый fetch на реальном сервере занял примерно 13 минут;
- разделить в документации:
  - первичную загрузку;
  - ежедневный --refresh;
  - частичное обновление одного игрока;
  - обновление меты и лиги;
- описать ожидаемое число запросов как зависящее от состава и параметров;
- задокументировать таймауты, rate limits, retries и возможную продолжительность;
- явно указать, что production должен работать за HTTPS reverse proxy;
- описать использование внешнего Caddy/nginx без запуска встроенного Caddy-профиля;
- документировать backup boundary: data/ воспроизводим, а .env и secrets не должны попадать в Git или image.

## Критерии приёмки

Перед завершением работы обязательно:

1. ./gradlew test успешно выполняется в чистом checkout.
2. docker build успешно завершается.
3. docker compose config успешно завершается.
4. Web запускается от non-root пользователя.
5. /health возвращает 200.
6. Без SITE_PASSWORD production Compose не запускает публичный web.
7. Порт 8070 публикуется только на loopback.
8. Первый fetch создаёт рабочий набор данных.
9. Повторный scheduled fetch действительно обновляет существующие файлы.
10. Ошибка в середине refresh не изменяет активную генерацию данных.
11. Два refresh-процесса не могут выполняться одновременно.
12. После успешного refresh web видит новую генерацию.
13. После неуспешного refresh web продолжает работать со старой генерацией.
14. В репозитории нет паролей, API keys, session secrets, production-data или иных секретов.
